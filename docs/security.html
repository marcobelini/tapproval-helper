Security: what Tapproval can see, and what was fixed

Tapproval answers permission prompts, so a bug in it is a bug in somebody's permission boundary. This page says what it can see, what it promises, what it does not protect against, and every security fix so far. The computer half is open source, so each claim here can be checked in the code.

What Tapproval can see, and where it goes

A small helper on your computer, Tapproval Base, sees what Claude Code asks permission for: the command, or the file and what would be written to it. For the session list it also reads Claude Code's transcripts on that computer. It sends a short card to your watch and prints your answer back to Claude Code. There is no server of ours, no account and no telemetry. Cards take one of three routes:

  • Your own network. Watch and computer talk directly.
  • Your own iCloud, if you install the Mac bridge. Cards pass through CloudKit's private database, which belongs to your Apple ID. We cannot read it.
  • An encrypted tunnel, if you turn on the travel connection. Traffic passes through Cloudflare and is not stored there. The address is secret, but it is only an address: every request must still prove a device key.

The privacy policy has the same routes, with what each part stores.

The rules it will not trade away

  • It approves nothing on its own by default. Allowing the harmless tiers automatically is something you switch on. A CRITICAL call is never auto-allowed, whatever the setting.
  • It fails closed. Anything it cannot parse, reach or judge ends with the ordinary prompt in your terminal, exactly as if Tapproval were not installed.
  • Only a process on your own computer is let in without a key, and even that process can post a card but never answer one, so a command Claude runs cannot approve its own prompt. Being on the same Wi-Fi counts for nothing: on a café network, that is a room full of strangers.
  • A current watch never sends its key. From TestFlight build 138 on, it signs each request. Each signature can be used once. The helper proves itself in its answer, and the watch keeps an address only from an answer carrying that proof.
  • Standard-library Python only. The helper installs no third-party packages, so there is no dependency tree to trust.

What it does not protect against

  • A compromised computer. A process running as you can talk to the helper. Letting local processes in is what lets Claude Code hand it a prompt in the first place.
  • Your Apple ID, on the iCloud route. With the Mac bridge, the watch learns its first key from your private iCloud. Anyone who controls your Apple ID could answer a prompt, so protect it with two-factor authentication.
  • What the audit log holds. The helper logs command text on your computer, with credential-shaped fragments removed. It never leaves the machine, but it is there.

Fixes, disclosed

Newest first. Each entry says what was wrong, when, who could have used it, and the fix. Starting Claude Code once updates the helper.

1.1.27, 27 September 2026: a request could borrow the key of the one before it

What was wrong. Several requests can share one network connection. The helper kept what it had learned about a request, including whether its key had been proved, on the connection instead of on the request. A request without a key, sent on a connection just after a request that did prove a key, was treated as proved.

Since when. From 1.1.21 (25 September 2026), when signed requests arrived, until 1.1.27.

Who could have used it. Only someone who knew your secret travel address. Cloudflare's tunnel shares connections between callers, so such a person's request could land on a connection your watch had just used, and read sessions or answer a prompt. Without the travel connection turned on, there was no way in.

The fix. Every request now starts from nothing and proves its own key. A test sends a keyless request after a signed one on the same connection and expects a refusal. Release notes.

1.1.21, 25 September 2026: the key stopped crossing the network

What was wrong. Before this, a watch proved itself by sending its key with each request, and it trusted any helper that answered on the right address.

Who could have used it. Someone able to read the traffic, or to answer in the helper's place on your network, could have learned the key.

The fix. Requests are signed and good once, and the helper proves itself in every answer. A Mac with the iCloud bridge never offers a key on the network. The network pairing door hands out a revocable device key rather than the main one. Watches from before signing, including the App Store version today, still send the key, so the helper still accepts it from them; that ends once the App Store version signs. Release notes.

Before the first public release, August–September 2026

  • The Wi-Fi was a credential. Anyone on the same network could read transcripts, answer a prompt, or type into a live session. Every caller except a local process now presents a device key.
  • The travel address was the key. The tunnel's secret path and the device key became separate secrets, so seeing the address grants nothing.
  • Pairing was reachable through the tunnel. On that route the caller looked local. The pairing door is now closed there.
  • A local command could answer its own prompt. Local processes may still post cards, but answering one now needs a device key.

Checking a download

From 1.1.27 on, each release carries an archive of its source and a signed statement from GitHub that the release workflow built that archive from the tagged commit. gh attestation verify tapproval-helper-v1.1.27.tar.gz -R marcobelini/tapproval-helper checks it. It proves where a release came from, not that the code in it is safe; for that, the code is there to read.

Reporting a problem

Open a private security advisory, or write to tapproval@thoughtfulsteward.org. You will hear back within a few days. There is no bounty, only credit if you want it, and a fix. What counts, and what is accepted, is in SECURITY.md.
